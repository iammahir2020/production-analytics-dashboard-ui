# Build Steps — Production Analytics Dashboard

Each step is a single, reviewable unit of work. Check it off after reviewing, then move to the next. Steps marked **(pause)** touch external/shared systems (GitHub, Vercel) and will always be confirmed before running, regardless of checklist state.

**Commit points:** marked with 🔖 at the end of a phase. These are *suggestions only* — commits are never made automatically. When we reach one, I'll say so and propose a commit message describing what that phase actually built; you decide whether and when to run `git commit`.

**Companion file:** [`learn.md`](learn.md) gets a new entry after every step — a plain-language explanation of what was done and why, building into a full study record of the build. Each entry includes a **Commands run** list: the actual shell commands executed for that step, with whatever flags/config/presets were passed — a real trace of what ran, not just a description of it.

**Before each step**, I give a short heads-up covering: what we're about to do, why this approach over the obvious alternative, what problem/mistake it's specifically guarding against, and how it moves the build forward. That's the forward-looking version; `learn.md`'s entry afterward is the record of what actually happened.

**Engineering standards held throughout (not one-off steps — applied continuously as each piece is built):**
- Debounce input handlers that trigger fetches or expensive work (e.g. the orders search box)
- Keep files small and single-purpose — split a component/module up rather than letting one file grow to do several jobs
- Paginate any list that can grow large (orders table); keep naturally-short lists (recent orders/activity on the dashboard) simple, un-paginated
- Any image that ends up in the UI goes through `next/image` (automatic compression/optimization) — flagged case by case if one comes up, since the current design doesn't require any
- No unnecessary re-renders; no dependency added without a real reason
- Keep code simple and direct — no over-engineering, no code that looks meaningful but isn't actually doing anything (see project memory on this)
- UI must read as deliberately designed — modern, distinctive, and polished, not a generic templated "AI slop" look. See the design checkpoint before Phase 2.
- **Server → Client Component props carry data or rendered elements, never functions.** A closure passed from a Server Component into a `"use client"` component's props builds and typechecks clean but throws at request time ("Functions cannot be passed directly to Client Components") — only actually running the server catches it. Pass a pre-rendered `ReactNode` instead (same mechanism `children` already uses). Relevant again for Phase 3's `FiltersBar`/`OrdersTable` split (Server shell feeding Client components) — found in Phase 2b's `ExpandableChart`
- **Every responsive grid/flex span gets an explicit value at the smallest breakpoint it applies to, not just the breakpoint being changed.** `lg:col-span-6` with no base span silently defaults to `col-span-1` below `lg` — it'll build, lint, and typecheck clean, and only show up on an actual narrow screen. Set the mobile-first span, then layer breakpoint overrides on top of it. Found in Phase 2b's `SummaryCards` hero tile
- **A skeleton changes in the same step as the real layout it shadows, never after.** A mismatched skeleton causes a visible layout jump when real content streams in — that's a regression, not a neutral omission
- **Any header/content that shares a corner with an absolutely-positioned control (a dialog close button, a corner overlay action) reserves explicit clearance for it.** Edge-to-edge content and a corner overlay don't coexist safely by default — found in Phase 2b's `ExpandableChart` modal header colliding with shadcn's `DialogContent` close button
- **After any visual/layout phase, do a real-screen review, not just a clean `build`/`lint`/`tsc`.** All four bugs above passed every automated check; none are the kind those tools can catch (one's purely visual, three are breakpoint- or runtime-conditional)
- **When two or more panels sit as siblings in the same grid row, check they actually match height, not just that the grid "should" stretch them.** `Suspense`/`SectionBoundary`/`ErrorBoundary` render no wrapping DOM element, so the grid's own `align-items: stretch` stops at each panel's outer wrapper `div` — the `<section>`/`Card` inside need explicit `h-full`/`flex-1` to actually fill it. Found between Order status/Top products and again between Recent orders/Recent activity
- **A page-wide layout value (container max-width, etc.) may exist in more than one independent place.** `app/layout.tsx`'s `<main>` and `components/shared/app-header.tsx`'s header row each hard-coded their own `max-w-*` — changing one without checking for the other would have misaligned the header against the page content. Grep for a value before assuming one edit covers it
- **Current type/density baseline for any new component (build against this, not Phase 2b's original tighter scale):** page container `max-w-7xl`; section headings 13px via the shared `<SectionHeading>` (`components/shared/section-heading.tsx`) — extract into it rather than re-typing the literal className a 6th time; body/list text 14–15px; card padding 16px (Card's own default — don't reach for `size="sm"` reflexively); chart/donut heights around 160px. Recalibrated from the original Phase 2b numbers, which were correct for fixing flatness but ended up calibrated against Linear's all-day power-user density rather than this app's actual "glanced at, not lived in" audience
- **A Recharts tooltip that needs more than the raw `dataKey`/`value`** (a real label, a matching color, anything from the underlying domain object) **reads it off `item.payload` in a custom `formatter`**, not off `name`/`value` alone — `name` is often just the raw data key. See `StatusDonut`'s tooltip for the pattern
- **"How many data dependencies does this page have" isn't the only Suspense-boundary question — "what UI must never be in the blast radius when that dependency refetches" is a second, separate one.** A page can have exactly one data dependency and still need a boundary narrower than the whole route, if something on it (a filter bar, any always-interactive control) doesn't itself depend on that fetch. Without that narrower boundary, the nearest `loading.tsx` fallback replaces the *entire* page on every refetch — unmounting and remounting live, focused inputs on every interaction. Found in `/orders`: fixed by splitting the data-dependent part into its own component (`OrdersResults`) under its own `<Suspense>`, with `FiltersBar` rendered outside it
- **A Base UI form primitive doesn't necessarily do the obvious thing by default — check its actual type, don't assume.** `SelectValue` renders the raw selected value, not the matching option's label, unless given an explicit `children` mapping function. Same category as `ToggleGroup`'s array-valued single-select from earlier — read the type (`find node_modules/@base-ui/react/<component> -iname "*.d.ts"`) before trusting an assumption carried over from a different library's API shape
- **Never combine an all-sides `border-{color}` utility with a directional one (`border-l-{color}`, `border-r-{color}`) on the same element — always use directional color utilities for every side that needs one, even the "default" sides.** `tailwind-merge` treats the all-sides utility as conflicting with the directional one and drops it entirely (not just the shared side) when the two appear together, silently leaving the non-overridden sides with no real color at all. Confirmed as a real shipped bug once already (the Phase 2b ledger) and caught again before shipping in the orders table's sticky column — worth checking for on sight now, not re-diagnosing from scratch each time it recurs
- **A `border` on a `position: sticky` cell inside a `border-collapse` table doesn't reliably repaint at its current scrolled position (worst in Chrome) — use `box-shadow` for any accent/edge on a sticky table cell instead.** `box-shadow` isn't part of the border model and isn't affected by `border-collapse` at all. Two insets can combine in one declaration (`inset 3px 0 0 0 {color}, inset -1px 0 0 0 var(--border)`) for a status stripe + edge separator together. See `components/orders/sticky-ledger-cell.tsx`, the shared component both ledger tables use for their sticky leading column
- **`notFound()` does not reliably produce an HTTP 404 status in the App Router — it depends on whether the response has already started streaming, and a route with any `loading.tsx` (or a page async enough to hit Suspense) almost always has.** Confirmed directly (not assumed): `curl -D -` against `/orders/<bad-id>` returns `200 OK` with the not-found UI in the body, both with and without `app/orders/[id]/loading.tsx` present — this is documented, not a bug (`node_modules/next/dist/docs/.../not-found.md`: "200 for streamed responses, 404 for non-streamed"). A real 404 status would need a pre-stream check (`proxy`, an experimental Cache Components pattern) — out of scope here. `notFound()` is still the right call: correct UI, a `noindex` meta tag, and a real limitation worth naming rather than silently shipping past. Found building Phase 4's `/orders/[id]`
- **`next/jest`'s alias resolution only covers `import` statements (via its SWC transform) — `jest.mock("@/...")` needs its own `moduleNameMapper` entry, confirmed missing by running `jest --showConfig`, not assumed from the docs.** A plain `import x from "@/lib/api/client"` resolved fine with zero config; `jest.mock("@/lib/data/mock-orders.json", factory)` in the same file threw `Cannot find module` — that call is a raw runtime string, never touched by the alias-aware transform. Fixed with one `moduleNameMapper: { "^@/(.*)$": "<rootDir>/$1" }` entry, mirroring `tsconfig.json`'s own `"@/*": ["./*"]`
- **`jest.mock(...)` calls are hoisted above every other top-level statement in the file, including a `const` declared physically above them — a factory that closes over such a const hits it before it's initialized.** Not a naming-convention problem (a `mock`-prefixed variable name doesn't rescue this under the SWC-based transform `next/jest` uses); the fix is structural — put fixture data directly inside the factory, or set it via a mocked function's `.mockResolvedValue(...)` inside `beforeEach`, never in a factory closing over a same-file const
- **`jest-environment-jsdom`'s global scope is missing `structuredClone`** — a real gap in that specific test environment, not a production concern (real Node 18+ and every modern browser have it). `lib/api/client.ts`'s `mockFetch` depends on it to clone mock responses; polyfilled in `jest.setup.ts` with a JSON round-trip, which is a faithful stand-in specifically because every value this app ever clones is already plain JSON (parsed straight out of `lib/data/*.json`) — no Dates, Maps, or circular references anywhere in its data types for a JSON round-trip to fall short on
- **Jest doesn't support rendering an `async` Server Component the normal way** (Next's own Jest docs say so directly: "we recommend E2E tests for async components"). Where one's still worth a component test (`SummaryCards`, which fetches its own data and takes no props), call the function directly and `await` the JSX it returns, *then* hand that already-resolved element to `render()` — by that point it's a plain synchronous element tree, which is all `render()` ever needed; no real RSC test runner required
- **A promise under `jest.advanceTimersByTimeAsync(...)` needs its `expect(...).resolves/.rejects` handler attached *before* advancing the timer, not after** — `mockFetch`'s `setTimeout` callback settles the promise the instant the fake timer fires, and a promise that rejects with nothing attached to it yet trips Node's unhandled-rejection detector even though a handler arrives on the very next line. Fixed by creating the `expect(...)` chain first (`const assertion = expect(promise).rejects...`), then advancing the timer, then awaiting `assertion`
- **With the Playwright MCP browser tools: `browser_navigate`, `browser_click`, and `browser_take_screenshot` all auto-wait for the page/network to settle before returning — `browser_evaluate` does not.** This made every first attempt at screenshotting a genuine loading/skeleton state fail (by the time any of those three tools returned, an artificially-delayed `mockFetch` had already resolved), including a Link click, which turned out to hit Next's router-cache/prefetch and skip the delay entirely regardless of wait behavior. The reliable pattern: `browser_evaluate(() => location.reload())` (a raw DOM call, not Playwright's own navigation action) returns immediately, *then* a following `browser_evaluate` (measuring via `getBoundingClientRect()`, more reliable than a screenshot for this) or a fast-enough screenshot can catch the transient state before it resolves. Confirmed working twice, independently, for both `/` and `/orders`
- **A skeleton's per-element bar heights need to match the real content's actual *rendered* line-height, not an intuitively-plausible smaller number** — found by directly measuring (not eyeballing) skeleton-vs-real card heights: `SummaryCards`' KPI row measured 88px in its skeleton vs 113px loaded (a 34px-font hero figure renders taller than its own nominally-inherited 20px line-height — browsers expand the line box for oversized glyphs rather than clip them, confirmed empirically), `TopProducts`/`RecentOrdersList`/`OrdersTable` were all using `h-3.5` (14px) bars against real `text-sm` content that actually renders at 20px. Also found a fully *missing* skeleton row (`OrderStatusBreakdown`'s cancellation-rate summary line) and a missing `<thead>` placeholder in two table skeletons — both are structural gaps a height-only check wouldn't catch. One inherent limit hit while fixing this: `RecentActivityFeed`'s real rows vary in height because message text sometimes wraps to two lines — a uniform skeleton can approximate the common case but can't match every real row exactly, and that's a property of the data, not a bug to keep chasing
- **Calling two URL-state setters back to back in the same handler can silently lose the first one.** `useOrderFiltersUrl`'s original `setFilter(key, value)` closed over one `searchParams` snapshot per call — `setFilter("from", x); setFilter("to", y)` in the same function both read the *same* pre-update snapshot, so the second `router.replace` overwrote the first's change entirely. Needed for the date-range picker (setting both endpoints from one Apply click); fixed by adding a `setFilters(updates)` that builds one `URLSearchParams` from every change and calls `router.replace` once, with the singular `setFilter` now a thin wrapper around it — not two independently-maintained code paths
- **`react-day-picker` (v10)'s range mode seeds a same-day range on the very first click, not a half-open one** — confirmed by reading `addToRange`'s own source (`node_modules/react-day-picker/dist/esm/utils/addToRange.js`): with the default `min={0}`, `{from: undefined, to: undefined}` + one click → `{from: day, to: day}`, both endpoints already non-null. Treating "both endpoints present" as "the user is done" (auto-commit-and-close) closed the popover after a single click, before a real second endpoint could ever be chosen. The standard, robust fix most real range pickers use: don't auto-commit selection changes at all — add an explicit Apply button and let the user decide when they're finished; sidesteps the seed-vs-complete ambiguity entirely rather than trying to out-guess the library's internal state machine
- **A shared error-fallback component needs the same height-matching treatment (`h-full`, and — new here — `justify-center` for actual vertical centering) as the success-state content it replaces, or a failed section next to a taller successful sibling leaves a real, measurable dead-space gap.** Confirmed via `getBoundingClientRect()`, not eyeballed: `SectionBoundary`'s fallback `Card` sat at its own natural 158px height inside a grid cell CSS Grid had stretched to 230px (via the *same* `align-items: stretch` mechanism that already correctly sizes successful content's own `h-full`/`flex-1`) — a 72px gap. One shared component fixes every dashboard section at once; verified in both height-relationship directions (Order status/Top products *and* the reversed Recent orders/Recent activity pairing) and against the neutral case (every section failing at once, where there's no taller sibling to stretch against) before trusting it as a general fix
- **A `Suspense` boundary only catches a thrown *promise* (the loading state) — a thrown *error* passes straight through it to the nearest actual error boundary, which for `app/orders/page.tsx` was the whole route's `error.tsx`, wiping out `FiltersBar` along with the failed results.** This was already correctly documented as an accepted limitation in the page's own comment, but confirmed directly what it actually looks like (forcing `getOrders()` to fail replaced the entire page, search box included) rather than trusting the comment at face value — the same "clunky filter" disruption a Suspense boundary alone already fixed for the *loading* case doesn't get fixed by that boundary for the *error* case; a **separate** client-side `ErrorBoundary` scoped to the same subtree is required (reused the dashboard's existing `SectionBoundary` rather than inventing a second mechanism)
- **`SectionBoundary`'s retry (`router.refresh()`) re-fetches every section's data on the page, but only resets the error UI of the section whose own Retry was clicked** (its `ErrorBoundary`'s `key` bump is what actually discards `hasError: true` — a different section's `ErrorBoundary` instance never remounts, so it keeps rendering its stale cached fallback even though fresh, successful data was just reconciled into its own unrendered `children`). Confirmed by deliberately failing all 6 dashboard sections at once and retrying them one at a time, watching each recover independently rather than assuming a single retry would revive everything — this is the exact, correct, already-documented trade-off, not a bug
